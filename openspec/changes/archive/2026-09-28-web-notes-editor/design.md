# Design

## Context

`apps/web/src/features/notes` already has an `api/notes-api.ts` (only `fetchNotes` today), a `hooks/` folder, and `components/` for the list page. Routing lives in `apps/web/src/routes/router.ts` as a flat `RouteObject[]`, with `RequireAuth`/`RequireGuest` wrapper components already gating children. `NoteCard` is a plain `Card`, not a link. `apiFetch` (`apps/web/src/lib/api-client.ts`) already normalizes errors and handles 401-refresh-and-retry; it's the only sanctioned way to call the API (per CLAUDE.md, no direct `fetch`/`axios` in components). `packages/shared` already exports `noteDtoSchema`, `createNoteRequestSchema`, `updateNoteRequestSchema` (`content: proseMirrorDocSchema`, a ProseMirror `{type: "doc", content: [...]}` shape), and `tagDtoSchema` - these match TipTap's `editor.getJSON()`/`editor.commands.setContent()` output directly, so no new shared schema work is needed. `apps/web/src/features/tags` already has `fetchTags`/`useTagsQuery` (`GET /tags`), and `NotesTagFilter.tsx` already shows the project's established toggleable-tag UI pattern (a `Badge`-as-button per tag, `aria-pressed`) that the editor's tag selector should mirror. `apps/web/package.json` already depends on `radix-ui` (the unified Radix primitives package), so a delete-confirmation dialog needs no new npm dependency - just a new `components/ui/alert-dialog.tsx`, following the same shadcn pattern as the existing `alert.tsx`/`card.tsx`. See proposal.md - Why / What Changes.

## Goals / Non-Goals

**Goals:**
- A working `/notes/:id` editor that loads a note, lets the user edit it with TipTap, and autosaves on idle without a manual save button.
- A visible save-status indicator so the user always knows whether their latest edit is persisted.
- Minimal navigation (card click, "New note" button) so the editor is actually reachable.
- A dedicated, autosaved title input above the editor canvas, without introducing a new API field or backend change.
- Tag assignment and note deletion available from the editor, so these already-implemented API capabilities aren't left unreachable from the frontend.
- No data loss on unmount or tab close while edits are unsaved.
- No lost keystrokes or cursor jumps caused by the editor's own background data refetching.

**Non-Goals:**
- Version history UI, sharing UI, search UI - all explicitly out of scope per proposal.md.
- Rich TipTap extensions beyond `StarterKit` (no tables, images, mentions, etc.) - nothing in the ticket calls for them, and `notes` API validation only constrains nesting depth and non-emptiness, which `StarterKit`'s node set satisfies trivially.
- Optimistic-concurrency / conflict resolution across multiple tabs or devices editing the same note - the API does last-write-wins today (`notes-history` spec) and nothing in this ticket changes that.
- A real, separate `title` field in the API or `packages/shared` - the `notes` spec explicitly forbids `title` as client input; this change works entirely within that existing contract (see Decisions).
- Any Playwright/e2e coverage for this change - Vitest + React Testing Library only, per explicit scope confirmed with the user.

## Decisions

**TipTap packages: `@tiptap/react` + `@tiptap/starter-kit` + `@tiptap/pm`, pinned exact versions.** `context.yaml` already names TipTap as the frontend's editor per the project's stated stack, so this isn't a new-library decision, just picking the packages. `StarterKit` bundles the baseline nodes/marks (paragraph, heading, bold, italic, lists, etc.) that produce a ProseMirror doc compatible with `proseMirrorDocSchema`'s `{type: "doc", content: [...]}` shape without any custom node config. `@tiptap/pm` is TipTap's re-export of the underlying `prosemirror-*` packages and is required as a peer for `@tiptap/react`.

**Autosave: a small `useAutosave` hook wrapping idle-debounce + TanStack Query mutation, not a library.** The project has no debounce utility and no autosave pattern yet. A ~15-20 line `useEffect`-based idle timer (reset on every `editor.on("update")`) that calls a `useMutation`-wrapped `updateNote` is small enough that pulling in a debounce library (e.g. lodash.debounce) would be more surface area than it saves, and keeps the retry/status state colocated with the existing TanStack Query mutation status (`isPending`/`isError`/`isSuccess`) instead of hand-rolling a parallel state machine. Alternative considered: a fixed-interval save loop - rejected per the user's explicit preference for idle-debounce (confirmed during exploration), and because it would autosave even when nothing changed, creating pointless `NoteVersion` snapshot churn (every content-changing `PATCH` snapshots the prior state, per `notes-history`).

**Save-status indicator built from existing UI primitives (`Alert`, plain text), not a new toast system.** The project has no toast/notification library (checked: not in `apps/web/package.json`). Adding one for a single inline status string would be disproportionate; an inline text/`Alert` region next to the editor is consistent with how errors are already shown elsewhere (e.g. auth forms).

**"New note" creates immediately via `POST /notes`, then navigates - no client-only draft state.** The alternative (a local-only "new note" that isn't persisted until first autosave) would mean the URL `/notes/:id` doesn't exist until a save happens, complicating routing and making the loading/not-found states ambiguous. Creating eagerly with an empty starter doc keeps `/notes/:id` meaningful from the moment the user lands on it, matches how the API already handles empty-content rejection (an empty starter doc must be a minimal valid non-empty ProseMirror doc, e.g. one empty paragraph node, not `content: []`), and reuses the exact same editor/autosave path for a brand-new note as for an existing one.

**`NoteCard` becomes a `react-router` `Link` wrapping the existing card markup**, not a wrapping `<button>` with `useNavigate`. Keeps it a real anchor (middle-click/open-in-new-tab "for free", better default accessibility) with no behavior change to the card's existing rendering.

**Title input is a UI-level view onto the document's first node, not a new API field.** The `notes` spec is explicit: `title` SHALL NOT be accepted as client input, and is always re-derived server-side from `content`'s first node. Introducing a real `title` field on `CreateNoteRequest`/`UpdateNoteRequest` would mean reopening and modifying that already-implemented, out-of-scope backend contract, and would duplicate a single piece of information across two representations (the field and the first node) - exactly what CLAUDE.md's "never duplicate types" guidance argues against. Instead, the title input and the body editor split one underlying ProseMirror document: the title input renders and edits `content.content[0]` as plain text, the body editor renders `content.content.slice(1)` as its own independent editable region, and autosave recombines `[titleNode, ...bodyNodes]` into one document before sending it - so the wire format and the API's derivation rule are untouched. The sync between the two is one-way only (title input -> first node): the body editor has no special handling of its own first line, and body edits never write back into the title input. An earlier draft of this decision described a two-way sync ("editing the body's first line updates the title input"), but that doesn't hold under a hard split - the body's first line is the document's *second* node, not the title's node, so there's nothing coherent for it to sync back to. Surfaced and resolved with the user during implementation; the spec's corresponding scenario was corrected to match. Alternative considered: a real separate `title` field, kept in sync with node 0 - rejected because it changes the `notes` capability's contract for no behavioral gain the API doesn't already provide. Alternative considered: one continuous editor with the first line styled as a title row (no separate `<input>`) - would make a two-way "same node" sync coherent, but is a bigger rework of an already-confirmed decision; not pursued.

**Tag toggle bypasses the autosave debounce and saves immediately.** Toggling a tag is a discrete, deliberate action (like a checkbox), not continuous typing - debouncing it would make the UI feel unresponsive and risks a toggle being silently lost if the user navigates away within the idle window. It reuses `updateNote` (the same `PATCH /notes/:id` used by content autosave) with the current content plus the new `tagIds`, and reuses the `NotesTagFilter`-style toggle UI (`Badge`-as-button, `aria-pressed`) already established on the notes list, rather than inventing a new tag-picker pattern.

**Delete confirmation uses a new `AlertDialog` component, not `window.confirm`.** `window.confirm` blocks the main thread, is unstyled, and is difficult to assert against in React Testing Library (it isn't part of the DOM tree). A Radix-based `AlertDialog` (via the already-present `radix-ui` package) matches the project's existing shadcn/ui component style, is keyboard-accessible by default, and is testable the same way the rest of the UI is.

**Flush-on-unmount and `beforeunload` share one "flush pending save" function, invoked from two places.** The autosave hook keeps a ref to the latest pending (unsaved) content. An unmount effect (cleanup function) calls that flush function once, fire-and-forget (not awaited, since an unmounting component can't usefully wait on it) - this covers in-app navigation (e.g. clicking another note or "New note"). Separately, a `beforeunload` listener registered only while the hook considers itself dirty calls `event.preventDefault()`/sets `event.returnValue` to trigger the browser's native confirmation for a tab close or full-page navigation, and best-effort fires the same flush function; it is removed as soon as the dirty state clears (including right after that flush resolves). These are two different scenarios (in-app unmount vs. leaving the page) that both reduce to "don't lose the pending save," so one shared flush function backs both rather than duplicating the save logic.

**Editor/query isolation: seed-once via a `noteId`-keyed effect, and `setQueryData` (not `invalidateQueries`) after a successful save.** `useQuery`'s `data` reference can change on any background refetch (refocus, reconnect, TanStack Query's own refetch-on-mount behavior) even when the fetched content is identical to what's already rendered. Calling `editor.commands.setContent()` every time that happens would reset the ProseMirror selection (cursor jumps) and can clobber keystrokes made between the refetch firing and resolving. Instead, a `useEffect` keyed only on the route's `noteId` param calls `setContent` once per note; subsequent query data changes for the same note are read by nothing but the initial seed. After a successful autosave `PATCH`, the mutation's `onSuccess` writes the response into the query cache via `queryClient.setQueryData(['note', noteId], response)` rather than `invalidateQueries`, which would otherwise schedule a refetch whose resolution could race with the user's next keystroke.

**TipTap pinned at the exact version `2.26.1` for `@tiptap/react`, `@tiptap/starter-kit`, and `@tiptap/pm`.** Verified via `npm view @tiptap/react@2.26.1 peerDependencies` (and the same for `@tiptap/starter-kit`/`@tiptap/pm`) that `2.26.1` is the latest published `2.x` release and its `peerDependencies` list `react`/`react-dom`: `"^17.0.0 || ^18.0.0 || ^19.0.0"`, matching this project's React `19.0.0`. `3.x` (currently `3.31.3`) also supports React 19, but is a new major version with API differences from `2.x`'s `StarterKit`/`useEditor` surface; picking the mature `2.x` line for this first TipTap integration avoids taking on that migration risk alongside every other change in this ticket. All three packages are pinned to the same `2.26.1` to keep `@tiptap/pm`/`@tiptap/core` (a `2.26.1` peer of `@tiptap/react`) in lockstep.

## Risks / Trade-offs

- **Frequent edits create frequent `NoteVersion` rows.** Idle-debounce (~1-2s) bounds this to roughly one snapshot per pause in typing rather than one per keystroke, but a long editing session still produces many versions over time. Mitigation: none needed in this change - `notes-history`'s auto-purge (already implemented per its spec) bounds retention; no new work required here.
- **Autosave failure while the user keeps editing.** If a `PATCH` fails and the user immediately makes further edits, the failed request's content is superseded by the next debounced attempt, which already carries the full latest document - so no separate "replay the failed request" logic is needed, only "don't lose local edits and keep trying." Covered by the spec's retry scenario.
- **A fire-and-forget flush on unmount/`beforeunload` isn't guaranteed to complete.** Browsers may abort an in-flight request when a tab actually closes, so the flush is a best effort, not a guarantee. Mitigation: the short (~1-2s) idle debounce already bounds how much unsaved content can exist at any moment to begin with, so at most a few seconds of edits are ever at risk even if a given flush doesn't land; the `beforeunload` confirmation also gives the user a chance to cancel the navigation and let the normal debounced save catch up.
- **Title/body split adds editor-state complexity.** Treating the first node specially (owned by the title input) while the rest of the document is owned by the body editor is more state to keep in sync than a single flat editor, even with the sync now one-way. Mitigation: component tests cover title -> first node sync, that body edits leave the title untouched, and tab/focus order between the two regions, so regressions surface as test failures rather than being noticed only in manual testing.
